# OpenTron Cherry-Pick Protocol System

## Project Purpose & Philosophy

This is a **self-contained protocol generator** for the Opentrons OT-2 liquid handling robot. The core philosophy is **configuration as embedded data**:

```
TOML configuration + CSV transfer maps → compiled JSON → embedded in self-contained Python protocol
```

**Key benefits:**
- Define liquid transfers in simple CSV files
- Configure deck layout in human-readable TOML files
- Generate complete protocols that run directly on the OT-2 with no runtime file dependencies
- Test everything with simulation before touching real samples

The system handles complex pipetting tasks like cherry-picking samples from multiple source tubes into specific destination wells with precise control over volumes, heights, flow rates, and tip management strategies.

**🆕 MCP Server Integration:** The system now includes a Model Context Protocol (MCP) server (`src/ot2_cherrypick_mcp/`) that exposes protocol generation through AI-native tools. This enables natural language interaction with the system while maintaining the human-readable TOML/CSV workflow.

## How the System Works

### The Three-File Workflow

**🟢 Files You Edit Often** (Every Protocol Run)
- **CSV files** (`CSVs/*.csv`) - Define what transfers to perform
- **settings.toml** - Deck layout, pipette mode, liquid handling parameters

**🟡 Files You Rarely Edit** (Only When Adding New Labware)
- **labware_dict.toml** - Labware catalog and calibration offsets

**🔵 Files You Never Edit Manually** (Auto-Generated)
- **CherryPick_OT2.py** - Final protocol with embedded JSON configuration

### The Compilation Process

When you run `./simulate_protocol.sh CSVs/your_file.csv`:

1. **helper_cherry_pick.py** reads TOML + CSV files
2. Converts them into a single compact JSON string
3. Embeds the JSON into `CherryPick_OT2.py` inside the `get_values()` function
4. **opentrons_simulate** validates the protocol without hardware
5. If successful, copies protocol to clipboard
6. Optionally (with `--send-to-opentrons`), overwrites protocol in Opentrons App directory

**Critical concept:** The `get_values()` function contains a single-line JSON string with ALL your configuration. The protocol is completely self-contained - no external files needed at runtime.

## Key Configuration Settings

### Pipette Modes (settings.toml)

**`mode = "single_X1"`**
- Single-channel pipette, one tip
- Each CSV row = 1 individual transfer
- Maximum flexibility for cherry-picking

**`mode = "multi_X1"`**
- 8-channel pipette in single-tip mode using `pipette.configure_nozzle_layout(style=SINGLE, start="H1")`
- Each CSV row = 1 individual transfer
- Useful when you have multi-channel hardware but need single-well precision

**`mode = "multi"`**
- 8-channel pipette, full 8-tip operation
- Each CSV row = 8 simultaneous transfers (entire column)
- When you specify well `A1`, it transfers the entire column (A1-H1)
- **Only works with 96-well and 384-well plates**

### Tip Reuse Strategies (settings.toml)

**`tip_reuse = "always"`**
- Use one tip for entire protocol
- Best for: Transferring same liquid type, minimizing tip waste

**`tip_reuse = "never"`**
- New tip for every transfer
- Best for: Preventing cross-contamination, different sample types

**`tip_reuse = "per_source"`**
- New tip when source labware changes
- Best for: Multiple source plates with different contents

### Head Speed (settings.toml)

```toml
[settings.general.head_speed]
speed = 400  # Movement speed in mm/min (100-600)
```

**Default:** 400 mm/min (recommended for most applications)

**When to reduce (200-300 mm/min):** Working with **very slippery or volatile solvents** (chloroform, hexane, organic solvents) that tend to leak or drip from the pipette tip during movement. Slower movement reduces vibration and sudden accelerations that cause droplets to escape.

### Liquid Handling Parameters (settings.toml)

These control the **physical techniques** for accurate liquid handling:

#### Pre-Aspirate Contact

```toml
[settings.liquid_handling.pre_aspirate_contact]
enabled = false
position_offset_percent = 20
aspirate_volume = 0  # Pre-wet volume (µL)
```

**Purpose:** Touch liquid surface and optionally pre-wet tip before aspirating target volume

**Scientific rationale:**
- **Pre-wetting (aspirate_volume > 0):** Coats inner tip surface with liquid. Critical for high surface tension or hydrophobic liquids. The first aspiration into a dry tip is often inaccurate due to evaporation and surface adhesion. Pre-wetting "primes" the tip.
- **Liquid contact (enabled = true, volume = 0):** Simply touches surface to detect liquid level and ensure proper positioning.

#### Post-Aspirate Tip Wicking

```toml
[settings.liquid_handling.post_aspirate_wick]
enabled = true
radius = 1         # Touch radius (mm, larger = closer to wall)
v_offset_mm = -1.5 # Height relative to well top (negative = below rim)
speed = 20         # Touch speed (mm/s)
```

**Purpose:** After aspirating, touch inside wall of well to remove external droplets hanging from tip

**Scientific rationale:** External droplets cause:
- Inaccurate volume delivery (liquid outside tip won't dispense correctly)
- Cross-contamination (droplets can fall off during movement)
- Dripping during transport

Similar to touching a manual pipette tip to well edge.

#### Post-Aspirate Delays

```toml
[settings.liquid_handling.delays]
post_aspirate = 0  # Wait time after aspiration (seconds)
```

**Purpose:** Pause after aspirating to allow liquid column inside tip to stabilize

**Scientific rationale:** Especially for viscous liquids, liquid continues flowing into tip briefly after plunger stops due to:
- Viscous flow lag (thick liquids move slower)
- Surface tension effects (liquid "pulling itself" into tip)
- Air pressure equilibration

**Recommended values:**
- Water/buffers: 0 seconds
- DMSO/glycerol: 2-3 seconds
- Oils/very viscous: 3-5 seconds

#### Push-Out Volume

```toml
[settings.liquid_handling.push_out]
enabled = true
volume_ul = 5  # Extra air volume to push (µL)
```

**Purpose:** After dispensing target volume, push out additional air to expel residual liquid

**Scientific rationale:** Mimics the "second stop" on manual pipettes. Viscous liquids and small volumes stick inside tip rather than being fully dispensed. Push-out:
- Expels residual droplets clinging to tip interior
- Ensures complete delivery of intended volume
- Compensates for surface tension holding liquid in tip

**Important:** NOT used when mixing follows dispense (mixing already agitates sufficiently)

**Recommended values:**
- 3-5µL: Most applications
- 8-10µL: Very viscous liquids
- Don't exceed 10µL (can cause splashing)

### Deck Layout Configuration (settings.toml)

**OT-2 Deck Slots:**
```
┌─────┬─────┬─────┬─────┐
│ 10  │  11 │ Trash│     │
├─────┼─────┼─────┤     │
│  7  │  8  │  9  │     │
├─────┼─────┼─────┼─────┘
│  4  │  5  │  6  │
├─────┼─────┼─────┤
│  1  │  2  │  3  │
└─────┴─────┴─────┘
```

**Configuration example:**
```toml
[[settings.working_plate]]
type = "source"
labware_id = "tube_rack_96_1500ul"
position_rack = "4"

[[settings.working_plate]]
type = "destination"
labware_id = "384_ppv_55ul"
position_rack = "2"

[[settings.working_plate]]
type = "tip"
labware_id = "opentrons_96_tiprack_300ul"
connection = "Pipette_8"  # Which pipette uses these tips
position_rack = "5"
```

**In CSV files, reference as:** `tube_rack_96_1500ul_4` (labware_id + slot number)

### Labware Calibration Offsets (labware_dict.toml) ⚠️ CRITICAL

Labware calibration offsets are **three-dimensional position adjustments** that fine-tune where the pipette moves relative to each labware.

```toml
[[labware]]
category = "plate"
labware_id = "384_ppv_55ul"
well_count = 384
well_volume = 55
offset_x = -0.50   # Negative = left, Positive = right
offset_y = 0.80    # Negative = front, Positive = back
offset_z = -0.30   # Negative = down, Positive = up
```

**Why they're critical:** Small variations occur due to:
- Manufacturing tolerances (±0.1-0.5mm even in identical labware)
- Deck positioning (labware doesn't always sit perfectly flush)
- Thermal expansion (plastic dimensions change with temperature)
- Wear and tear

These tiny misalignments cause:
- Tips crashing into well edges
- Liquid dispensed onto edges instead of into wells
- Incomplete aspiration
- Cross-contamination between wells

**Two calibration methods** (mutually exclusive):

1. **Define offsets in labware_dict.toml (Recommended)**
   - Apply automatically to all instances of that labware type
   - Embedded in protocol file
   - No operator intervention during setup
   - Version-controlled with TOML config

2. **Calibrate through Opentrons App during protocol setup**
   - If offsets NOT in TOML, operator must run "Labware Position Check"
   - Manually jog pipette to correct position
   - Saves offsets in robot's internal database
   - Starting with Opentrons v6.0.0+, offsets can be reused across protocols for same labware/slot/robot

## CSV Transfer Format

### Required Columns

| Column | Description | Example |
|--------|-------------|---------|
| `Source Labware` | Labware ID + slot | `tube_rack_96_1500ul_4` |
| `Source Well` | Well position | `A1`, `H12` |
| `Volume (ul)` | Transfer volume | `50`, `100.5` |
| `Dest Labware` | Labware ID + slot | `384_ppv_55ul_2` |
| `Dest Well` | Well position | `B1`, `P24` |

### Height Columns (Choose ONE per source/dest)

**For Source:** Use EITHER `Source Height` OR `Source Top` (never both)
- `Source Height` - Distance from well bottom (mm): `2`, `5.5`
- `Source Top` - Distance from well top (mm, negative goes down): `-5`, `-2.0`

**For Destination:** Use EITHER `Dest Height` OR `Dest Top` (never both)
- `Dest Height` - Distance from well bottom (mm): `1`, `2.5`
- `Dest Top` - Distance from well top (mm, negative goes down): `-3`, `-7.5`

**Best practice:** Use consistent heights for same labware type throughout CSV. All wells in same labware have identical geometry.

### Optional Advanced Columns

| Column | Default | Description | Example |
|--------|---------|-------------|---------|
| `Mix Volume` | 0 | Volume to mix after dispense (µL) | `20`, `50` |
| `Mix Height` | 2.0 | Mixing height from bottom (mm) | `1.5`, `3.0` |
| `Flow Aspirate` | 1.0 | Aspiration speed multiplier | `0.5` (slow), `1.5` (fast) |
| `Flow Dispense` | 1.0 | Dispense speed multiplier | `0.8` (slow), `2.0` (fast) |
| `Air Gap` | 0 | Air gap volume to prevent dripping (µL) | `10`, `20` |
| `Air Gap Rate` | 1.0 | Air gap aspiration speed | `0.5`, `1.0` |
| `Tip Action` | auto | Override tip management | `new`, `keep`, `drop` |

### CSV and Pipette Mode

**Important:** CSV structure looks the same for all modes, but interpretation differs:

- **single_X1 / multi_X1 modes:** Each CSV row = 1 individual transfer
- **multi mode:** Each CSV row = 8 simultaneous transfers (entire column). Well name `A1` means column 1 (wells A1-H1)

## Development Workflow

uv run python your_script.py

- Automatically manages the local `.venv/` environment
- Ensures consistent dependencies across all runs
- No need to manually activate/deactivate environments

- Fast, Rust-based package resolution

### Standard Workflow

**Option A: Traditional Script-Based Workflow**

1. **Edit CSV file** - Define your transfers
2. **Configure settings.toml** - Set deck layout, pipette mode, liquid handling
3. **Run simulation:** `./simulate_protocol.sh CSVs/your_file.csv`
4. **Deploy to OT-2:** `./simulate_protocol.sh CSVs/your_file.csv --send-to-opentrons`

**Option B: MCP-Based Workflow (via Claude Desktop or mcp-use)**

Both workflows produce the same CherryPick_OT2.py protocol file.

### Script Configuration (simulate_protocol.sh)

At top of script, set machine configuration:

```bash
MACHINE_CONFIG="local"  # or "remote"
```

Each configuration defines four key variables:

#### 1. LABWARE_PATH_WIN (Windows path to custom labware)
```bash
LABWARE_PATH_WIN="C:\Users\ricca\AppData\Roaming\Opentrons\labware"
```
- Points to where Opentrons App stores custom labware JSON files
- Script auto-converts to WSL format (`/mnt/c/Users/...`)

#### 2. TARGET_PROTOCOL_SRC_WIN (For --send-to-opentrons)
```bash
TARGET_PROTOCOL_SRC_WIN="C:\Users\ricca\AppData\Roaming\Opentrons\protocols\ea8382af-2299-4bc5-b556-81524aa7d0b6\src"
```
- Points to Opentrons App protocol source directory
- UUID part (`ea8382af...`) is generated by Opentrons App when you create/import a protocol
- Must include `\src` at the end
- Script auto-converts to WSL format

**To find your protocol UUID:**
1. Navigate to `C:\Users\{YourUsername}\AppData\Roaming\Opentrons\protocols\`
2. Each UUID folder corresponds to one protocol in the app
3. Check modification dates or look inside `src\` folders to identify which protocol

**Why Windows paths?** Convenience - copy-paste directly from Windows File Explorer. Script handles conversion automatically using `wslpath`.

**Note:** With the uv-based workflow, the ENV_EXE and ENV_NAME variables are no longer needed since uv automatically manages the local `.venv/` environment based on the `pyproject.toml` configuration.

### Using --send-to-opentrons

```bash
./simulate_protocol.sh CSVs/your_file.csv --send-to-opentrons
```

This automatically:
1. Simulates the protocol
2. Overwrites the protocol in your configured Opentrons App directory
3. Preserves the original filename

**Requirements:**
- `TARGET_PROTOCOL_SRC_WIN` must be configured correctly
- Path must point to valid Opentrons protocol `src` directory
- Directory must contain exactly one `.py` file

### Troubleshooting

| Error | Fix |
|-------|-----|
| Labware not found | Check `api_id` in `labware_dict.toml` matches Opentrons library |
| Slot conflicts | Verify unique `slot` values in `settings.toml` working_plate array |
| Multi mode incompatible | Multi mode requires 96 or 384-well plates only |
| Volume warnings | Ensure volumes within pipette `volume_range` |
| Both height columns | CSV must use EITHER Height OR Top, never both |
| Labware instance not found | CSV references `labware_id_X` but slot X not in `settings.toml` |

## Best Practices & Guidelines

### Coding Standards

- **Python 3.12** with four-space indentation
- **Module-level docstrings**: Summarize deck layout, consumables, safety notes
- **Naming**: `snake_case` for functions/files/CSV columns; `PascalCase` for classes only
- **Helper functions**: Keep pure and side-effect free; pass configuration explicitly
- **Operator feedback**: Emit concise `print()` statements for progress tracking

### Testing & Validation Workflow

1. **Always simulate after changes:** `./simulate_protocol.sh <csv>`
2. **Archive simulation output** for review and troubleshooting
3. **For liquid handling changes:** Schedule OT-2 dry run before production
4. **Document dry runs:** Capture calibration steps, deck photos, deviations in `projects/<experiment>/`
5. **Never hand-edit** the embedded JSON in `CherryPick_OT2.py` - always regenerate with helper

### Experiment Documentation

Use `projects/<experiment>/` directories to archive:
- CSV snapshots
- Jupyter notebooks
- Figures and visualizations
- Simulation logs
- Robot run notes and observations
- Maintains full provenance and reproducibility

### Version Control

- **Conventional Commits**: `feat:`, `fix:`, `chore:` with <60 char subjects
- **Never create commits** as an AI agent - only repository owner commits
- **Before committing new labware**: Perform calibration dry runs to verify offsets
- **Keep sensitive data out** of repo - share redacted/anonymized CSVs externally
